# PR 自查与后续风险

## 已发现并修复

- 原 PR 修改首页主标题后没有同步更新语言切换测试；CI 在 WebKit 测试阶段失败。更新文案断言后，CI 又暴露电话亭布局问题：WebGL 延迟加载时 WebKit 会让自动宽度受 canvas 固有尺寸影响，导致电话亭横向偏移。正在约束容器宽度与尺寸包含，保留原动画；WebKit 结果以 CI 为准，本地环境无法下载浏览器。
- 管理页此前先显示数据库模式再异步取作品，网络慢时登录并保存可能覆盖数据库。现在作品加载完成后才允许进入编辑。
- 此前编辑名称或技术栈会同时覆盖中英文内容。现在分别编辑并保留另一语言。
- 此前每个数据库请求都执行建表与种子检查、取得事务锁。现在每个函数实例只初始化一次，失败后允许重试；不同实例首次初始化仍通过 PostgreSQL 锁确保安全。
- 无数据库时此前 POST/PUT 返回 200，容易被误认为写入成功。现在只读模式查询返回 demo，写请求明确失败。
- 原 PR 没有真实数据库集成测试。现增加 CI PostgreSQL 服务，验证首次建表/种子、登录、拒绝未授权和跨域写入、数据校验、持久化以及空列表不重新播种。

## 当前架构与仍需注意

- 静态首页使用内置项目作为首屏和 API 故障时的回退；因此数据库故障时可能展示旧的内置内容，而不是最新数据。这不是数据丢失，但可能误导访客。后台不会因此进入预览模式。要严格消除旧内容，需要设计加载/错误状态，并评估对现有首屏和动画的影响。
- 管理 API 使用共享密码和签名 cookie，尚无服务端登录速率限制、用户管理或审计日志；公网部署应额外启用 Netlify 访问限制或速率限制，并使用高强度密码。仅修改密码不会撤销已有会话，需要同时轮换 `SESSION_SECRET`。
- 保存是整个列表的事务替换，没有乐观并发控制。两个管理员同时编辑时，后保存者可能覆盖先保存者；目前建议一次只在一个窗口编辑。后续应增加版本号和冲突提示。
- 首次连接时数据库用户需要建表权限，且需要 PostgreSQL 支持事务和 advisory lock。每个冷启动实例会检查初始化；数据库规模增长后应考虑独立迁移系统。
- 作品图片仍是旧站的占位图，GitHub 名称、日期和技术栈才是整理出的真实资料。应在后台替换成项目截图；本后台不托管或上传图片。GitHub 统计只涵盖当时能搜索到的公开提交。
- 数据库返回的作品在浏览器加载后才替换静态 HTML；搜索引擎或禁用 JavaScript 的访客可能看到内置内容。若 SEO 要求数据库内容实时可索引，应改用服务端渲染或部署时生成。
- 当前测试覆盖数据库函数的主要路径，但仍需要在真实 Netlify 站点验证函数打包、连接配置、HTTPS cookie、预览和正式部署环境隔离。不要让 Deploy Preview 与生产共用同一个数据库及管理员密钥。
